# Typed composition shortcuts

## Decision

Fronts exposes one transport-neutral composition value and three independent factories:

- `HostComposition` in `@fronts/core` pairs a typed application-reference catalog with a Host.
- `createMfHost()` in `@fronts/mf` builds that composition over an official Module Federation
  runtime.
- `createReactBindings()` in `@fronts/react` binds any composition to React.
- `createVueBindings()` in `@fronts/vue3` binds any composition to Vue 3.

The framework packages do not depend on `@fronts/mf`, and `@fronts/mf` does not depend on either
framework. The shared value is deliberately small:

```ts
interface HostComposition<Contracts, Source, Services extends object> {
  readonly applications: ApplicationCatalog<Contracts>;
  readonly host: FrontsHost<Source, Services>;
}
```

The runtime catalog retains normalized `AppRef` defaults such as a non-default expose. Its type also
keeps the props contracts invariant, so compositions with identical names but different props
cannot be rebound accidentally. There is no new runtime protocol, global default Host, or fused
React-plus-MF package.

## When to use this API

Use the shortcuts when a shell genuinely needs the Fronts Host: capability-scoped services,
resolution policy, DOM/Shadow DOM/iframe containers, readiness-gated replacement, cancellation, or
leak audit. They remove composition ceremony but preserve those boundaries.

If a fixed React or Vue remote only needs framework or router integration, use the official Module
Federation Bridge. If code only needs `loadRemote()`, use the official runtime directly. The
[decision record](decision-record.md) defines that boundary.

## Quick start

The producer remains a normal Fronts application exposed through the producer's official Module
Federation plugin:

<!-- typecheck: services -->

```tsx
import { defineReactApp } from '@fronts/react';

export interface CheckoutProps {
  readonly cartId: string;
}

function Checkout({ cartId }: CheckoutProps) {
  return <h2>Cart {cartId}</h2>;
}

export default defineReactApp<CheckoutProps, HostServices>({
  name: 'checkout',
  capabilities: ['navigation', 'telemetry'],
  root: Checkout,
});
```

The shell declares its integration contract once. Prefer props types generated by Module
Federation's type tooling over a second handwritten copy:

```ts
import type { CheckoutProps } from 'checkout_remote/application';

export interface ShopContracts {
  readonly checkout: CheckoutProps;
}
```

Compose delivery and React at module scope:

<!-- typecheck: contracts, services -->

```tsx
import { createRoot } from 'react-dom/client';
import { createMfHost } from '@fronts/mf';
import { createReactBindings } from '@fronts/react';

import type { ShopContracts } from './contracts.js';

const composition = createMfHost<ShopContracts, HostServices>({
  name: 'shop-shell',
  apps: {
    checkout: {
      remote: 'checkout_remote',
      entry: 'https://cdn.example.com/checkout/mf-manifest.json',
      version: '2.4.1',
    },
  },
  services: {
    navigation: { go: (path) => history.pushState(null, '', path) },
    telemetry: { emit: (name, data) => console.info(name, data) },
  },
  capabilityPolicy: ({ capability, identity }) =>
    capability !== 'navigation' || identity.name === 'checkout',
});

const shop = createReactBindings(composition);
const Checkout = shop.component('checkout', {
  container: 'shadow',
  loading: <p>Loading checkout…</p>,
  fallback: ({ error, retry }) => (
    <section role="alert">
      <p>{error.message}</p>
      <button onClick={retry}>Retry</button>
    </section>
  ),
});

const root = createRoot(document.getElementById('root')!);
root.render(<Checkout cartId="C-42" />);

window.addEventListener(
  'beforeunload',
  () => {
    root.unmount();
    void composition.host.dispose();
  },
  { once: true },
);
```

`createMfHost()` owns delivery composition. `createReactBindings()` only borrows the returned Host
and catalog. The component factory is called outside render, so `Checkout` has stable component
identity and its public props are exactly `ShopContracts['checkout']`.

React consumes `key` before component props reach the component. An application props contract
containing `key` is therefore intentionally excluded from `shop.component()`; use
`<shop.App app="..." props={{ key: ... }} />` so the contract stays nested and reaches the remote
application intact.

## Core composition contract

`ApplicationCatalog<Contracts>` maps every logical application name to a normalized reference. The
catalog is the runtime bridge between delivery and rendering:

```ts
interface ShopContracts {
  readonly account: { readonly accountId: string };
  readonly checkout: { readonly cartId: string };
}

const applications: ApplicationCatalog<ShopContracts> = {
  account: { name: 'account' },
  checkout: { name: 'checkout', expose: './checkout-application' },
};
```

The contract values have no runtime schema. They make the name-to-props relationship statically
checkable; the catalog supplies only names and `AppRef` defaults at runtime. `HostComposition`
contains a private optional type marker to keep props contracts invariant without requiring a
runtime branding property.

Transport factories return a fully typed composition. A manually assembled Host can be annotated
directly, or bound through the explicit curried framework form:

```ts
const composition: HostComposition<ShopContracts, Source, HostServices> = {
  applications,
  host,
};

const react = createReactBindings(composition);
const explicitReact = createReactBindings<ShopContracts>()({ applications, host });
```

The curried form is an intentional contract assertion for a manually assembled composition. The
direct form is preferred for a value already typed as `HostComposition`, especially a
`createMfHost()` result.

## Module Federation composition

### Static deployments

`createMfHost()` accepts a complete `apps` map keyed by `Contracts`. Each value is one deployment or
a non-empty ordered candidate list:

<!-- typecheck: shop -->

```ts
const composition = createMfHost<ShopContracts>({
  name: 'shop-shell',
  apps: {
    account: [
      {
        match: { channel: 'canary' },
        remote: 'account_next',
        entry: 'https://cdn.example.com/account/next/mf-manifest.json',
        version: '6.0.0',
      },
      {
        remote: 'account_stable',
        entry: 'https://cdn.example.com/account/stable/mf-manifest.json',
        version: '5.1.0',
      },
    ],
    checkout: {
      remote: 'checkout_remote',
      entry: 'https://cdn.example.com/checkout/mf-manifest.json',
      expose: './checkout-application',
      metadata: { isolation: 'iframe' },
      version: '2.4.1',
    },
  },
});
```

`RemoteDeployment` supports the official remote fields `remote`, `entry`, `type`, `alias`,
`entryGlobalName`, and `shareScope`, plus Fronts integration fields:

- `expose` defaults to `./application`;
- `version` becomes resolved identity and conflict evidence;
- `metadata` becomes frozen resolved deployment metadata;
- `force` and `preload` pass to the existing MF adapter behaviour.

All candidates for one logical application must use the same expose. Framework bindings retain one
catalog reference per logical name, so allowing candidate-specific exposes would make a later
`preload()` or mount ambiguous. Invalid static configuration is rejected before an automatic MF
runtime is created.

Candidate matching uses the existing static resolver fields: `range`, `channel`, `environment`,
`tenant`, and `cohort`. Candidates are evaluated in order; an entry without `match` is a fallback.

<!-- typecheck: shop -->

```tsx
<shop.App app="account" props={{ accountId: 'A-1' }} selection={{ ref: { channel: 'canary' } }} />
```

`selection.ref` changes the normalized application identity, while `selection.resolve` supplies
policy context without entering identity. Do not vary a ref selector merely to reach the same
deployment: that would correctly remount under a different identity but would not change the
loaded artifact.

### Registry-backed resolution

A platform resolver remains first-class. It must be paired with a catalog because a resolver alone
cannot tell a framework binding which logical names and expose defaults are valid:

<!-- typecheck: shop, federation -->

```ts
const composition = createMfHost<ShopContracts, HostServices>({
  name: 'shop-shell',
  runtime,
  applications: {
    account: {},
    checkout: { expose: './checkout-application' },
  },
  resolver: registryResolver,
  services,
  capabilityPolicy,
});
```

`apps` and `resolver` are mutually exclusive. Moving from static deployment candidates to a
registry changes the composition root; the contracts, binding, and component call sites remain the
same.

### Host and runtime options

All `FrontsHostOptions` except `loader` and `resolver` pass through: services, service providers,
capability policy, containers, container-specific loaders, timeouts, deterministic identifiers,
observers, and test clocks. `name` becomes the default Fronts `hostId`.

The factory either receives `runtime` or calls the official `createInstance()` with
`runtimeOptions`, `runtimeName ?? name`, and an empty initial remotes list. The result exposes all
three composition resources:

```ts
interface MfHostResult<Contracts, Services extends object> extends HostComposition<
  Contracts,
  ModuleFederationSource,
  Services
> {
  readonly runtime: ModuleFederation;
}
```

`name` and `runtimeName` are separate because Fronts Host identity and the official MF instance name
belong to different namespaces.

## React bindings

The direct overload infers contracts, Source, and Services from the composition. The curried
overload establishes Contracts explicitly for manual composition:

<!-- typecheck: shop -->

```ts
const react = createReactBindings(composition);
const manual = createReactBindings<ShopContracts>()({ applications, host });
```

The returned object has three operations:

```ts
interface ReactBindings<Contracts, Source> {
  readonly App: ReactAppComponent<Contracts, Source>;

  component<
    Name extends ApplicationName<Contracts>,
    Request extends ContainerRequest = BuiltInContainerRequest,
  >(
    name: Name,
    defaults?: ComponentDefaults<Contracts[Name], Source, Request>,
  ): ComponentType<Contracts[Name]>;

  preload<Name extends ApplicationName<Contracts>>(
    app: Name,
    options?: PreloadOptions,
  ): Promise<void>;
}
```

Use `App` when the application name or controls vary per render:

<!-- typecheck: shop -->

```tsx
<react.App
  app="checkout"
  props={{ cartId }}
  container="dom"
  selection={{ resolve: { tenant: tenantId } }}
/>
```

Use `component()` when controls are stable. Defaults may contain selection, container, loading,
fallback, equality, callbacks, target attributes, wrapper attributes, trace, and timeout. They
cannot contain `instanceId`, because one component type may be rendered more than once. Use `App`
when an external instance identity is required.

`BoundAppProps` is a distributed union over application names. This matters for a union name:

<!-- typecheck: shop, expect-error -->

```tsx
declare const selected: 'account' | 'checkout';

// Rejected: checkout props are not safe when `selected` may be account.
<react.App app={selected} props={{ cartId: 'C-42' }} />;
```

A generic indexed access would widen props to a union and incorrectly accept that call. The
distributed object union preserves the correlation.

`preload()` reconstructs the same catalog reference and passes the same selection policy to the
Host. A later mount still resolves again; preloading is an optimization, not a pinned rollout
decision.

## Vue bindings

Vue uses the same composition and lifecycle model:

<!-- typecheck: shop -->

```ts
const vue = createVueBindings(composition);
const Checkout = vue.component('checkout', {
  container: 'shadow',
  fallback: ({ error, retry }) => h('button', { onClick: retry }, error.message),
});
```

`createVueBindings()` has the same direct and curried overloads, plus `App`, `component()`, and
`preload()`. Stable factories return `FunctionalComponent<Props>`.

Like React, the inline `App` can be specialized for a custom container request in a render function:

<!-- typecheck: shop -->

```ts
const IframeApp = vue.App<IframeContainerRequest>;

const IsolatedCheckout = defineComponent({
  setup: () => () =>
    h(IframeApp, {
      app: 'checkout',
      container: iframeContainer,
      props: { cartId: 'C-42' },
    }),
});
```

Vue templates cannot supply TypeScript type arguments. For a custom container used from a template,
bind the request type through `component<Name, Request>()` instead. In a template, pass an object
with camel-cased contract keys when the generated functional component has no runtime prop schema:

<!-- typecheck: shop -->

```vue
<script setup lang="ts">
const Checkout = vue.component('checkout', { container: iframeContainer });
const checkoutProps = { cartId: 'C-42' };
</script>

<template>
  <Checkout v-bind="checkoutProps" />
</template>
```

Vue keeps in-place reactive prop mutations observable. Replacing a prop object with an equal one is
suppressed by the same equality contract as React.

## Containers and selection

Both bindings accept concise built-in containers:

```ts
component('checkout', { container: 'dom' });
component('checkout', { container: 'shadow' });
```

The shorthands map to frozen `{ type: 'dom' }` and `{ type: 'shadow', mode: 'open' }` requests.
Custom requests remain generic so their required fields are preserved:

```tsx
const IsolatedCheckout = react.component<'checkout', IframeContainerRequest>('checkout', {
  container: iframeResolver,
});
```

The shortcut never guesses an iframe URL, `targetOrigin`, or sandbox flags. Static deployment
`metadata` can supply trusted deployment-specific input to an explicit container resolver, as the
[React host example](../examples/react-host/src/runtime.ts) demonstrates.

The `Selection` split is intentional:

```ts
interface Selection {
  readonly ref?: Pick<AppRef, 'range' | 'channel'>;
  readonly resolve?: ResolutionPolicyContext;
}
```

`ref` participates in identity, audit, and conflict detection. `resolve` carries environment,
tenant, cohort, and metadata policy but does not change application identity by itself. The app name
and expose come from the typed catalog and cannot be overridden at a render site.

## Change detection

Bindings reuse the existing React and Vue host adapters rather than introducing another update
layer.

| Input                                            | Equality                      | Effect when changed        |
| ------------------------------------------------ | ----------------------------- | -------------------------- |
| Application props                                | Shallow own-key comparison    | Calls `update()`           |
| App name, expose, range, channel                 | Field value                   | Remounts                   |
| Resolution policy                                | Nested-shallow for plain data | Remounts                   |
| Static container request                         | Nested-shallow for plain data | Remounts                   |
| Container resolver                               | Function identity             | Remounts                   |
| `instanceId`, `traceId`, timeout                 | Value                         | Remounts                   |
| Loading, fallback, callbacks, wrapper attributes | Render value/ref              | Does not remount by itself |

Plain objects and arrays are compared structurally to the documented depth. Dates, DOM nodes,
class instances, and other opaque objects compare by identity; treating them as empty structural
records would hide real changes. Functions compare by identity at every depth. `arePropsEqual`
overrides the application-props comparison.

## Lifecycle, errors, and ownership

Bindings preserve the low-level Host contract:

1. Render starts resolution, load, container preparation, mount, and readiness.
2. Loading UI remains until application readiness succeeds.
3. Changed props update the retained instance rather than remounting it.
4. Wrapper unmount aborts pending work and unmounts the application.
5. `retry()` starts a fresh operation; it never resumes a partial mount.
6. Fallback and `onError` receive the real error. A `FrontsError` retains `code` and `phase`.
7. Replacement, activation, inspection, audit, and disposal remain on `host`.

An unknown logical application name is a binding configuration error, not a Host lifecycle failure.
Rendering throws before creating `RemoteApp`, and `preload()` rejects before calling the Host. In
React or Vue rendering, the error therefore reaches the nearest framework error boundary or error
handler instead of the local `fallback`/`onError`. Those controls apply after a valid catalog
reference starts Host resolution, loading, mounting, or updating.

Bindings borrow the Host. They expose no `dispose()` and must not dispose it from a component
cleanup. The composition root calls `host.dispose()` after unmounting its framework root.

The official MF runtime has a separate lifecycle constraint. `createInstance()` records created
instances in the runtime's global `__INSTANCES__` array, and the public API has no general destroy
operation paired with it. The default instance ID includes `Date.now()` only when no version or
explicit ID overrides it; the registry is an array, not a timestamp-keyed map.

Multiple runtime instances may be deliberate. The rule is therefore not “one runtime globally” or
“at most one per React root”; it is that every creation must correspond to an intentional,
bounded composition lifetime. Reuse or inject a longer-lived `runtime` when HMR, tests, or shell
recreation would otherwise call the factory repeatedly. `host.dispose()` does not pretend to remove
an MF instance through a non-existent public destroy API.

See [Host Runtime API](host-runtime-api.md) for the complete ownership and shutdown contract.

## Package boundaries

```text
@fronts/core    framework- and transport-neutral contracts, Host, HostComposition
@fronts/mf      official MF runtime adapter and createMfHost()
@fronts/react   React producer/host adapter and createReactBindings()
@fronts/vue3    Vue producer/host adapter and createVueBindings()
```

There is no horizontal dependency between sibling adapters. Producers continue to use official MF
bundler plugins; the shortcuts do not parse manifests, select shared dependencies, or add a build
abstraction.

## Compatibility and non-goals

The low-level APIs remain supported: `createFrontsHost()`, `createModuleFederationAdapter()`,
`createModuleFederationSource()`, `RemoteApp`, and `useRemoteApp()` are not deprecated. A shell can
migrate only its composition root; producer modules require no change.

The shortcuts do not:

- discover a Host or runtime through an import-order flag;
- create a Fronts-specific bundler plugin;
- fetch a registry unless the caller supplies that resolver;
- infer iframe trust settings;
- mirror every Host operation onto the binding object;
- turn Fronts into a router or SSR framework.

Fronts is still in the 2.0 prerelease line. The new factories are recorded as minor changes. Existing
adapter behaviour remains available for incremental migration.
